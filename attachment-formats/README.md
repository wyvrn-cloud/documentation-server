# Attachment formats

issue-credential and present-proof don't define what a credential, a credential request
or a proof looks like. Their messages carry those as attachments in a registered format,
named by an identifier: a DIDComm v1 message lists it in `formats[].format` next to the
attachment's `@id`; a DIDComm v2 attachment has it in its own `format`. This folder holds
JSON Schemas for those attachments' contents, which the registry serves with each
protocol that uses them (`attachment_formats` in a documentation/1.1 `response`).

Generated by [`scripts/gen-attachment-formats.py`](../scripts/gen-attachment-formats.py) (needs `pip install jsonschema json5`), which also checks every example payload in the RFCs and the WACI profile against them; edit the script, not the files.

- [`formats.toml`](formats.toml): every format (`id`, `title`, where it's documented),
  and for each message that carries it, the protocols it's used in. `[attachments]` names
  the attachment decorator of each DIDComm v1 message (`offers~attach`, ...).
- `<format id>/<message>.json`: the schema of the attachment's content in that message,
  i.e. the JSON in `data.json`, or decoded from `data.base64`. One format can have
  different content in different messages: `dif/presentation-exchange/definitions@v1.0`
  is a bare presentation definition in `propose-presentation`, but `{options,
  presentation_definition}` in `request-presentation`.

The Indy formats are v1-era and listed for the 2.0 protocols only; their AnonCreds
successors cover both.

## How strict they are

They check what the defining documents require, and leave the rest open: the parts
another specification owns (an AnonCreds key correctness proof, a W3C credential's
claims, a presentation definition's constraints) are only checked for shape. W3C
credentials are checked for the properties every credential has (`@context`, `type`,
`credentialSubject`, `issuer` and, once issued, `proof`), in data model 1.1 or 2.0.

Every example payload in the RFCs and the WACI profile that isn't clipped validates,
except RFC 0881's SD-JWT, which is the placeholder `eyJhbGciOiJFUzI1NiJ9.eyJfc2QiOi...(clipped)...~`.
